# v9-t / v10-t 接口与策略利用审计

核对日期：2026-10-07，北京时间。仅只读分析用户给出的结果 ZIP；没有发模型探针、启动评测、修改平台设置或策略源码。经 Kenny 授权发布分析归档；对话接续见 [CONVERSATION_CHECKPOINT.md](CONVERSATION_CHECKPOINT.md)。

## 结论

这次不能再归类为“模型全部调用失败”。v9 有 709 次成功完成的模型响应，v10 有 547 次。接口基本可用，但部分卡实际收到 Kimi `HTTP 403 / quota_5h`，同时成功回复的策略利用率很低。这是两类问题：服务侧的五小时用量限制，以及我们异步调度、回复有效期和决策接入的不足。

HTTP 错误本身不能归因于我们的 JSON 解析失败；`llm_client.py` 只在捕获 `urllib.error.HTTPError` 后计入状态，`quota_5h` 分类要求服务响应正文出现 `5-hour usage limit`。本包不保存原始错误正文，因此判断依据是已记录状态、脱敏类别和对应分类代码。档案不能确认实际使用哪位提供者的 key，也无法证明额度由本次评测独自耗尽。不能据此断言“老师的公益服务坏了”或赛事平台故障。

## 我们这边的具体不足

1. v10 策略建议回复在 A/C/D 分别有 76/48/39 次被判过期。模型策略成功响应为 104/54/41 次，最终策略动作变化为 15/4/0 次；过期规则涉及事件键、夜晚和有效期。该现象支持“异步回复与模拟时间推进配合不好”，尚不能仅凭聚合日志定位哪一个判定条件错误。
2. v10 天气预测在 A/C/D 分别有 61/35/18 次过期，当前 epoch 的接受包为 10/5/0。保存下来的天气统计组全部 `trusted=false`，有效 `mixture_weight=0`。这些预测没有建立优于规则的证据，不能直接提高权重当作修复。门槛是否过严、预测是否无效、时效是否不足，需要分开诊断。
3. v10 保存 19 个 `model_effects`，并有对应真实观测反馈；动作涉及时长、program 和指向。因此“完全没有实际影响”也不成立。但动作变化数很少，反馈没有未执行原动作的对照，不能证明这些变化有收益。
4. 恶劣卡仍有大量 REQUIRED 漏观测。v9 A1/B1/C1 分别漏 843/2090/1018 个，罚分 -42150/-104500/-50900；v10 分别漏 1079/2008/1058 个，罚分 -53950/-100400/-52900。这暴露确定性策略的弱天气安排问题，不能把整体低分全交给模型服务解释。

成功调用仍主要是在生成夜间建议和策略提案，而不是每个成功回复都会改变观测。v10 的动作计数是对已记录的直接改动作路径的统计，不穷尽天气状态间接影响。它也不代表评分收益。

## 责任和下一步

服务侧需要解决的是实际 key 对应的五小时额度可用性；接口地址和模型名称这次已经有成功证据，无需继续凭分数猜测是否通了。

我们需要处理的是：减少低收益重复请求；让跨动作仍有效的信息及时被采用，对仍未过期的未来窗口局部验收；优先保障恶劣卡值班日志解析；核查策略提案在哪个有效期或事件变化上被丢弃；独立改进 REQUIRED 的天气适应。不能靠放宽所有校验或强制增大 LLM 权重掩盖问题。

本轮只完成诊断，没有实施这些后续设计。v11 上一轮修复的是共享 program 搜索与 CPU 字段，不包含新的异步时效修复，不能预先说 v11 会解除本次问题。
