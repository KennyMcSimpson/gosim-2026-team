## 来源与取舍

用户已确认 76c437d3 使用 v3.zip，沿用了 v2 显示名称。此前 v3 失败分析显示
A/B/C 提前耗尽 900 标准化 CPU 秒，B 的 REQUIRED 缺失占主要损失。
本版以独立 v3-recovery 为数值底座，接入最新 v2-pi-pro 的实际 Pi 1.0.3 工具循环。
不是把失败的原 v3 直接加上模型，也不把 v2-Pi 的框架迁移称作已验证收益。

## 更新内容

- 保留 recovery 的真实 CPU 截止搜索、缓存几何、完整科学基线与一个紧急请求布局。
- 曝光排序计入有正确秒数单位的决策机会成本，不再按错误量纲放大短曝光优势。
- 已饱和目标可继续响应新请求；截止搜索时保留合法部分进展，真实结果才更新账本。
- 从已计算方案中保留至多 36 个不同取舍代表，Pi 每次最多比较六个方案。
- Pi 在当前决策选择候选 ID、状态 token 和受限理由；Python 验证数值依据、状态和几何。
- 保留 85% 估计收益下限；均匀度/短曝光为 98%。这不是实际分数保证。
- 多步或部分请求底座不被单步评审替换，避免模型错比后续收益。
- 当前方向公告同步解释为另一模型环节，故障确认沿用 recovery 的多次证据门槛。
- 每季最多 24 次方案评审与 8 次公告解读，额度随季节释放；最多 64 次总模型调用。
- 单问一次模型、一次工具、8 秒模型窗口，保留 300 秒墙钟；CPU 不超过 24 秒时不再调用。
- 连续三次 worker/模型失败后停用模型，继续确定性规划。
- Linux 优先读取容器 cgroup CPU；无法读取时合并 Python 和 Node OS 进程计数。
  计数不可用时按两核乘请求耗时保守扣除。Node 的 HTTP 等待本身通常不消耗 CPU。
- 固定 Node 22.20.0 在平台构建时校验下载；Pi bundle 与许可证直接随包提供。

- 26 项测试通过：状态 token、非法 ID、无 key、收益约束、pending、真实 worker CPU、
  cgroup 不重复扣除、CPU 余量、连续失败熔断、worker 崩溃与多步请求保护。
- recovery 五类回归、请求召回（74 秒曝光、重叠奖励与多步请求）、编译检查通过。
- 12 种无模型配置、四卡共 48 个动作与 pending 与冻结 recovery 相同。
  此处统一关闭时间截止以隔离逻辑差异，不表示生产截止下逐动作完全一致。
- 解压后的实际 Pi 1.0.3 + Node 22.20.0 + 本地模拟 SSE 选中三个非基线动作。
  动作通过官方光纤/几何检查，pending 与动作一致。
- 四个实际 agent.py 子进程覆盖 9/16/25/100 光纤，stdout 只输出 JSONL-v4 协议，
  且当前公告环节确实走 Pi 工具。
- 非法候选与纯文本工具失败各只有一次 HTTP 尝试；超时终止 worker 并回退。
- 冻结 recovery 原目录的哈希再次确认未变。

测试 provider 全为本地模拟，无真实模型调用、隐藏 truth、正式/练习评分、平台上传或 GitHub 推送。

## 上传设置

上传 `v4.zip` 到官网完整项目入口。默认 `AGENT_MODEL_BACKEND=pi-pro`；若网页沿用的
变量里有 `AGENT_MODEL_BACKEND=v2`、`disabled` 或 `PI_ENABLED=0`，须改为 `pi-pro`、`1`。
模型配置沿用队伍的 `OPENAI_BASE_URL`、`OPENAI_MODEL` 和运行时 key。ZIP 不含凭据。
`disabled` 可用于 recovery 对照；`v2` 指 recovery 配原 HTTP 建议器，并非原始 v2 策略。

线上应先查看终止原因与整季完成，再比较总分、科学分、REQUIRED 缺失、请求完成、作废、
CPU/墙钟与实际 plan_review 应用。旧版本保留用于同模型设置对照。
